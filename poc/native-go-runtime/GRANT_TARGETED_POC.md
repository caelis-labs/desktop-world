# Directed exact-window authorization: isolated POC checkpoint

Base of the first checkpoint: `670bdf66a71c0500deed4d9b3adf2d85bf8dec97`. That checkpoint changed no helper, backend, or public authorization contract. The later `4c177e4` section records a build-tagged isolated helper/backend POC; the default product helper and public contract remain unchanged. The early diagnostic resolver below returns a **candidate**, never a grant or an AX action target.

## Observed failure, separated by layer

`internal/helper/authorization.go:155` refreshes a pending title declaration with one whole-desktop AX summary. Lines 225–239 discard all matches if any unrelated app/window makes the inventory incomplete, dirty or truncated. The title then stays `unresolved/discovery_incomplete`; a complete scan with no matching AX window reports `pending/application_not_running`. That pending state says only that the AX selector was not found, not that the process or native window does not exist.

On the current signed, owned standard `NSWindow` Target, the exact title exists in CGWindow and the App's own log confirms the window is visible. Five consecutive whole-desktop AX detail/summary samples were clean, but AX summary found zero exact windows. A direct `AXWindows` read for this PID returned one element equal to the `AXApplication` root, with title `DTW Focus Target`, rather than the actual window. A real Go MCP → QuickJS → native-helper `dtw.grants()` test returned `pending/application_not_running` three times and did not dispatch an action. Raw sample hashes and fixture PID/binary identity are in [evidence](evidence/grant-targeted-670bdf.json). Earlier sessions also returned `unresolved/discovery_incomplete`; the two outcomes must not be conflated.

The existing native `capture_windows` directory supplies an independent identity. A whole-desktop capture directory included the exact owned title but was itself incomplete (`capture_window_budget` from another window). The **same** directory scoped to the unique owned App Ref was complete, clean and contained exactly one native capture window; a second fresh scoped query retained the same Ref. This Ref is bound in the backend to PID, process-start identity, native window ID and live window presence (`internal/backend/darwin/capture_darwin.h`). It is intentionally separate from AX windows and cannot be used as an AX click target or joined to one by title/bounds alone. [The candidate resolver](internal/grantcandidate/resolve.go) rejects incomplete zero matches, dirty positives, duplicates, owner mismatch and a changed native Ref. Its result is explicitly `candidate_only`.

## Minimum safe authorization path

1. The trusted host identifies the intended process instance and exact native window, preferably from a user-selected window or an owned launched fixture, and retains PID/process-start/window ID. Script arguments cannot expand this declaration. An app name alone is insufficient when multiple instances exist.
2. Resolve the native window within that process using a complete, fresh **process-scoped** directory. A partial global catalog may offer a lead but never proves uniqueness or absence. A complete app-scoped zero match remains pending until the host can establish window closure; an incomplete zero match stays unresolved. Recheck the same identity before every dispatch and expire, rather than rebind, on process exit or window replacement.
3. Resolve any AX action Ref independently to the same native window through a trustworthy native mapping. The current public AX/capture API deliberately has no window-ID join; title or geometry equality alone is not enough. If the mapping or AX target is unavailable, refuse the foreground action. A native receipt with `delivery:complete` is not proof of an App callback.
4. Enforce the exact window scope on **every** action at the helper boundary. Today `ApplicationGrant` retains only an App Ref and `turnGrants.Check` accepts any target with that App owner (`internal/helper/control.go:113`). Merely replacing the discovery step with a capture candidate would grant writes to other windows in the App. This is a separate authorization change required before declaring the fix passed.
5. Keep status, cancellation and original receipts available through the sole public MCP `exec` tool. Unknown delivery is reconciled under the original ID and never blindly replayed.

Apple's [`NSWorkspace.OpenConfiguration.activates`](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/activates) was set to false for the fixture launches; the fixture and probe logs report no front/key transition during those launches. A one-time quiet-gated `NSRunningApplication.activate` request returned false and did not bring the Target forward. After the user's voluntary interaction with the standard owned window, the **same PID** became front/key, and `AXWindows` changed from an `AXApplication` root to one real `AXWindow` with the exact title. A fresh real MCP grant became `active`; clean app-scoped reads then found one exact window. The temporal comparison supports an activation-sensitive AX exposure on this host, but it does not prove that one title-bar click is generally required or solve background-only grant discovery.

With that now-visible owned window, two isolated Go MCP/QuickJS/native runs semantically set and read the controlled value, captured a window PNG, and performed one foreground click each. The native receipts reported `complete` and `restored`, and the App log gained exactly one `submit` callback per run with `matches_expected:true`. A test assertion initially looked for a deliberately unlogged `field_value`; it was corrected to use callback count and the fixture's in-process equality flag. The first action was not replayed. Two distinct Session processes then contended on the same App with nonoverlapping lock intervals and one callback each; a third round cancelled a waiting Session B while A alone produced one callback. A full model task loaded the isolated Skill, used only MCP `exec`, wrote/read the value and clicked once; the App log independently recorded its one callback. [Bounded checkpoint evidence](evidence/grant-targeted-670bdf.json) gives exact hashes and limitations.

None of those owned-App effects validates steps 3–4 of the proposed **general exact-window authorization repair**. The current helper still binds a title declaration to an App Ref, so another window in that App would be inside its current action boundary. Distinct-App physical seat contention, automated background-only activation, live user takeover during an actual borrow, pointer restoration, and all-provider behavior remain unproved. Read-only global discovery internally enumerated desktop metadata, but the diagnostic output and committed evidence retain only the owned fixture and aggregate counts; no unrelated App contents were acted on.

## 001b1b4 follow-up: native identity and the remaining authorization boundary

The new [bounded evidence](evidence/window-identity-distinct-app-001b1b4.json) uses two separate owned AppKit bundles. A read-only process-scoped probe obtained `PID + proc_bsdinfo start time + _AXUIElementGetWindow ID`, then checked each ID against exactly one same-PID CGWindow. A never-front/key two-window process exposed two distinct AXWindows/IDs; a real MCP title grant for its first window became active and app-scoped reads were clean. Three one-window background controls also exposed AXWindow, including a plain `NSWindow` and an `orderBack` window. The earlier app-root result is therefore **not a universal macOS background AX restriction**. The specific cause of that earlier instance remains unresolved; timing, process registration, and fixture lifecycle have not been separated. A complete global discovery page is not required to prove the identity of a stable, process-scoped target, but the current helper still uses global AX inventory to bind a declaration.

The POC-only [`exactgrant` model](internal/exactgrant/grant.go) binds PID, process start, native window ID, App Ref and AX Window Ref, then refuses a sibling window in the same App, a missing AX mapping, a mixed-target plan, replacement, closure or PID reuse. Its tests pass, but **it is not connected to the running helper**. The public `dw.Intent` contains `Targets` and `Applications`, with no trusted native window identity. `turnGrants.Check` consequently cannot enforce this model. A title match still stores `o.App`; changing only discovery would silently broaden the authority. The minimum integration is a trusted native Ref→AX window→native ID resolution at the helper action boundary, with fresh process/window-lifetime checks for every step. If any mapping is unavailable, the action must remain denied. This must be proven live on a same-App two-window fixture before the exact-window grant row can pass. The `_AXUIElementGetWindow` mapping is an existing macOS SPI in the cooperative backend, so its availability and platform scope need explicit handling; title or bounds are never an identity fallback.

One distinct-App foreground round after fixing a **fixture-only** JSON logger crash had Session B acquire the shared seat, complete one click, get one independent owned callback and restore the prior foreground; its key-window interval was 100.5 ms. Session A waited, then returned `user_active/never_automatically` without acquiring or clicking. The activity source was not sampled outside owned fixtures. The earlier two-process `user_interrupted` result coincided with both fixtures crashing at `NSJSONSerialization _writeJSONNumber` from nonfinite activation-event location metadata; it was a fixture failure, not evidence of human takeover. Two successful distinct-App callbacks, live mid-borrow user takeover, and pointer preservation remain unpassed. Neither round changed helper authorization semantics.

## 4c177e4 follow-up: exact identity at the real POC action boundary

The isolated `dtw_poc_exactgrant` build now connects the model to the **real helper authorizer**, after the original turn/App authorization check and before each engine action step. The native resolver receives an engine-owned backend key, walks only same-PID direct `AXWindow`/parent links, calls the existing macOS `_AXUIElementGetWindow` SPI, and requires exactly one live same-PID CGWindow ID. It joins that key back to the same world App and AX Window Refs and retains `PID + proc_bsdinfo process start + native window ID + App Ref + AX Window Ref`. Each action re-resolves both its target and the bound window; an unknown, changed or closed identity denies before dispatch. No title, geometry, frontmost-window fallback, or script-supplied ID is used for authority. The default helper build does not compile this hook. Explicit host App/Name grants retain App scope; a title declaration has no App fallback in the POC gate.

Real Go MCP `exec` → QuickJS → helper rounds on one owned two-window App passed three checks. A safe already-empty `set_value('')` against the sibling returned `permission_denied`; the **original** receipt was stopped with `delivery:none`, and the sibling field stayed empty through that round. A semantic Unicode set on the approved window completed and verified with one App text-change callback. A separate explicit App Name grant then set and cleared the sibling field, both verified, showing App scope still works when expressly granted. Finally, the fixture closed the bound native window and created a new same-title window without activation. Both the old Ref and freshly observed replacement Ref were denied `permission_denied`; old/new native window numbers differed. The post-replacement grant-status recheck was then added and unit-tested, but the live replacement round preceded that status-only patch, so its live status presentation remains unverified. [Bounded evidence](evidence/exactgrant-action-boundary-4c177e4.json) records owned PIDs, callback order, log hashes, action results, and this binary-hash limit.

The background discovery failure was independently reproduced **before helper pagination**. Direct PID-scoped `AXWindows` on two new owned single-window Apps and a unique-bundle control returned an element equal to `AXApplication` while CG listed the exact on-screen native window. The caller's AX trust bit was true. `AXMainWindow`, `AXFocusedWindow`, App-scoped hit testing, and `AXChildren` also produced App/menubar elements, no AXWindow or valid `_AXUIElementGetWindow` ID. A real new MCP grant stayed `pending/application_not_running` on three refreshes and dispatched no action. An earlier owned PID that had exposed two correct AXWindow IDs later returned two App roots without a front/key transition. Thus the observed result is temporally variable and not explained by a single-window class, bundle-ID collision, dirty desktop page, or lack of a CG window. The exact AX provider/registration cause remains unresolved; CG title/bounds alone cannot substitute for an AX action identity. The existing host title declaration still uses the global inventory before the POC gate can bind, so unrelated global incompleteness can still delay otherwise stable exact targets. A targeted candidate-PID discovery path would need to create a verified engine App/Window Ref from native AX elements and keep the original grant/revoke boundary; it cannot resolve the current App-root samples without trustworthy AXWindow exposure.

Two new owned distinct-App fixtures were prepared for the next physical-seat round, but both had this direct App-root result. No pointer or foreground action was dispatched. The two-successful-callback contention, live user takeover, pointer restoration, Windows runtime, and full baseline therefore remain unpassed; product migration stays prohibited.

## ebdc0ba AX isolation and target-lookup implication

The [owned-fixture diagnosis](evidence/ax-provider-remoting-ebdc0ba.json) rules out a scanner pagination or short messaging timeout explanation for the current App-root samples. A fresh standard NSWindow is an `AXWindow` to its own live AppKit provider; an instrumented `accessibilityWindows()` override was called on the provider main thread and returned that native window 20 times. Yet the external trusted AX reader got the App root as its sole `AXWindows` element through both direct and paged APIs. A prior successful FocusFixture binary and a uniquely identified first-instance Launch Services registration reproduced the same result. The fault is observed between provider return and usable remote AX window identity; its exact OS/registration trigger remains unknown. A 159 ms activation request did not become foreground, so successful activation has not been isolated. These facts narrow the boundary without claiming all TCC, providers or OS releases are sound.

The minimum repair remains one trusted process-scoped target lookup reused by host title declaration and per-action checking. It must produce a live engine AXWindow Ref joined to PID, process-start identity and native window ID; it must respect the same grant, revocation and expiry record. Global inventory incompleteness from unrelated Apps must not decide a unique target once that trusted lookup succeeds. When the provider supplies only App roots, the lookup has no authoritative AX action target; status stays pending/denied. CGWindow title or geometry is only a candidate hint, and explicit App grants remain a separate, intentionally wider scope. No permission reset, new TCC request or synthetic window identity is justified by this diagnosis.
