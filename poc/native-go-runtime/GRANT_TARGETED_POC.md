# Directed exact-window authorization: isolated POC checkpoint

Base: `670bdf66a71c0500deed4d9b3adf2d85bf8dec97`. No product helper, backend, or public authorization contract is changed by this checkpoint. The diagnostic programs under this directory are read-only except for launching and stopping their own fixtures. The resolver below returns a **candidate**, never a grant or an AX action target.

## Observed failure, separated by layer

`internal/helper/authorization.go:155` refreshes a pending title declaration with one whole-desktop AX summary. Lines 225–239 discard all matches if any unrelated app/window makes the inventory incomplete, dirty or truncated. The title then stays `unresolved/discovery_incomplete`; a complete scan with no matching AX window reports `pending/application_not_running`. That pending state says only that the AX selector was not found, not that the process or native window does not exist.

On the current signed, owned standard `NSWindow` Target, the exact title exists in CGWindow and the App's own log confirms the window is visible. Five consecutive whole-desktop AX detail/summary samples were clean, but AX summary found zero exact windows. A direct `AXWindows` read for this PID returned one element equal to the `AXApplication` root, with title `DTW Focus Target`, rather than the actual window. A real Go MCP → QuickJS → native-helper `dtw.grants()` test returned `pending/application_not_running` three times and did not dispatch an action. Raw sample hashes and fixture PID/binary identity are in [evidence](evidence/grant-targeted-670bdf.json). Earlier sessions also returned `unresolved/discovery_incomplete`; the two outcomes must not be conflated.

The existing native `capture_windows` directory supplies an independent identity. A whole-desktop capture directory included the exact owned title but was itself incomplete (`capture_window_budget` from another window). The **same** directory scoped to the unique owned App Ref was complete, clean and contained exactly one native capture window; a second fresh scoped query retained the same Ref. This Ref is bound in the backend to PID, process-start identity, native window ID and live window presence (`internal/backend/darwin/capture_darwin.h`). It is intentionally separate from AX windows and cannot be used as an AX click target or joined to one by title/bounds alone. [The candidate resolver](internal/grantcandidate/resolve.go) rejects incomplete zero matches, dirty positives, duplicates, owner mismatch and a changed native Ref. Its result is explicitly `candidate_only`.

## Minimum safe authorization path

1. The trusted host identifies the intended process instance and exact native window, preferably from a user-selected window or an owned launched fixture, and retains PID/process-start/window ID. Script arguments cannot expand this declaration. An app name alone is insufficient when multiple instances exist.
2. Resolve the native window within that process using a complete, fresh **process-scoped** directory. A partial global catalog may offer a lead but never proves uniqueness or absence. A complete app-scoped zero match remains pending until the host can establish window closure; an incomplete zero match stays unresolved. Recheck the same identity before every dispatch and expire, rather than rebind, on process exit or window replacement.
3. Resolve any AX action Ref independently to the same native window through a trustworthy native mapping. The current public AX/capture API deliberately has no window-ID join; title or geometry equality alone is not enough. If the mapping or AX target is unavailable, refuse the foreground action. A native receipt with `delivery:complete` is not proof of an App callback.
4. Enforce the exact window scope on **every** action at the helper boundary. Today `ApplicationGrant` retains only an App Ref and `turnGrants.Check` accepts any target with that App owner (`internal/helper/control.go:113`). Merely replacing the discovery step with a capture candidate would grant writes to other windows in the App. This is a separate authorization change required before declaring the fix passed.
5. Keep status, cancellation and original receipts available through the sole public MCP `exec` tool. Unknown delivery is reconciled under the original ID and never blindly replayed.

Apple's [`NSWorkspace.OpenConfiguration.activates`](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/activates) was set to false for the fixture launches; the fixture and probe logs report no front/key transition during those launches. A one-time quiet-gated `NSRunningApplication.activate` request returned false and did not bring the Target forward. After the user's voluntary interaction with the standard owned window, the **same PID** became front/key, and `AXWindows` changed from an `AXApplication` root to one real `AXWindow` with the exact title. A fresh real MCP grant became `active`; clean app-scoped reads then found one exact window. The temporal comparison supports an activation-sensitive AX exposure on this host, but it does not prove that one title-bar click is generally required or solve background-only grant discovery.

With that now-visible owned window, two isolated Go MCP/QuickJS/native runs semantically set and read the controlled value, captured a window PNG, and performed one foreground click each. The native receipts reported `complete` and `restored`, and the App log gained exactly one `submit` callback per run with `matches_expected:true`. A test assertion initially looked for a deliberately unlogged `field_value`; it was corrected to use callback count and the fixture's in-process equality flag. The first action was not replayed. Two distinct Session processes then contended on the same App with nonoverlapping lock intervals and one callback each; a third round cancelled a waiting Session B while A alone produced one callback. A full model task loaded the isolated Skill, used only MCP `exec`, wrote/read the value and clicked once; the App log independently recorded its one callback. [Bounded checkpoint evidence](evidence/grant-targeted-670bdf.json) gives exact hashes and limitations.

None of those owned-App effects validates steps 3–4 of the proposed **general exact-window authorization repair**. The current helper still binds a title declaration to an App Ref, so another window in that App would be inside its current action boundary. Distinct-App physical seat contention, automated background-only activation, live user takeover during an actual borrow, pointer restoration, and all-provider behavior remain unproved. Read-only global discovery internally enumerated desktop metadata, but the diagnostic output and committed evidence retain only the owned fixture and aggregate counts; no unrelated App contents were acted on.
