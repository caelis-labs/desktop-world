The default response retained `complete:false`, `truncated:true`, `more:true`; `result` retained the original native reply. - Three **real background AppKit semantic control** scenarios passed through the new chain: `set_checked`, `set_selected`, and `set_expanded` each ran true, repeated true, false, true. Each native action reported semantic channel, verified state, no foreground borrowing; the repeated true was `delivery:not_applicable`, with no extra App callback. These are controlled App effects, beyond receipt-only evidence.
- Two independent MCP Sessions/native helper processes wrote the **same owned App** with nonoverlapping cross-process lock intervals (541/535 ms in the final reference-isolation round); both writes reached the App. On two **different owned Apps**, lock intervals overlapped (543/555 ms) and each App received its own write. Session B's attempt to use Session A's native Ref returned `permission_denied` and no foreign value reached either App. During another same-App contention, cancelling waiting Session B prevented its write while Session A completed one real write. These prove background parallelism, same-App serialization, Ref isolation and one-sided cancellation for the tested path. Physical foreground arbitration is still unproved.
- A real background semantic write reached an owned App once, then the waiting JS execution was cancelled before its deliberately delayed native reply. ## Foreground and user-input failure

The original FullFixture test (preceding checkpoint) had one submit callback with `POC-中文🙂画`, after a native read of `POC-中文🙂`; its cause remains unknown. The user was operating the desktop then, so misdirected real/IME input is plausible but unproven.

This checkpoint added an owned focus/input-logging App and saved [an original click receipt](evidence/focus-round-c-original-receipt.json). Across ten controlled clicks, the native receipt reported `outcome:completed`, `delivery:complete`, `channel:foreground_transaction`, `restoration:restored`; foreground occupation was 119–260 ms (median 128.5 ms). **Zero of ten** produced the target App's submit callback or local pointer event. During recorded borrowing the target PID briefly became frontmost/active while the App window's `isKeyWindow` stayed false. This is a failed business-effect gate; native `verification:not_requested` never meant the submit was verified.

The six-round attempted real-user-input comparison is **invalid** for mistargeting probability: target and Human fixture windows initially occupied the same coordinates, and the Human fixture logged zero keys. The user reported that the Human window could not be focused or clicked and that DTW moved the mouse. We stopped the foreground rounds and terminated both owned fixtures. The fixture now places the Human window separately, defaults it to foreground, primes its text field, and redacts text from both fixture logs. [The build script](build-focus-fixtures.sh) produces two distinct, locally signed macOS app bundles with separate bundle identifiers; compilation, plist and signature validation passed.

In a **Human-only follow-up without DTW**, the bundle launched but was initially visible without being active or key. A separate `open -a` activation made it frontmost and key. The user could then click the window but twice could not enter text, including a double-click followed by one digit. Its old local-monitor log counted zero mouse/key events and maximum field length 0 despite seven key-window transitions. The raw local log was not committed; [bounded metadata](evidence/human-focus-followup.json) was. That run used binary SHA-256 `98922758...`, which **predated** the `NSWindow.sendEvent` instrumentation. Thus it could not have produced a `window_input` record. The missing window record does not establish where input went.

The [fixture diagnostic audit](evidence/human-fixture-diagnostic.json) bound the old, unrun intermediate, and fixed bundles to exact binary hashes and separated their PIDs. The old app's 4,633 timer samples and key/main notifications prove its AppKit loop and log writes were running; the old absence of local monitor events still has no established cause. The newer intermediate bundle had a **fixture bug**: it read `NSEvent.keyCode` for a mouse event. A controlled in-process mouse self-test crashed PID 28607 with `SIGABRT`; the native crash stack includes `-[NSEvent keyCode] → closure in Fixture.applicationDidFinishLaunching → FixtureWindow.sendEvent`. The fixed bundle (`c304fec8...`) conditionally reads keyCode only for keyboard events. A self-posted event then reached both the local monitor and `NSWindow.sendEvent`; a direct window send was also logged. A separate direct process PID 28726 stayed non-frontmost and non-key throughout this test. This validates the **recording mechanism**, not physical human typing. No new real-user keyboard test has occurred on this fixed build.

One `open -g -n` launch of that fixed bundle returned before its log appeared, then unexpectedly started PID 28700 and briefly activated its window. The log captured only event types, timing, coordinates and field length, no text. We closed both exact owned PIDs and stopped further visible diagnostics. `open -g` plus `window.orderBack` is therefore not a dependable no-focus test setup on this host. No DTW foreground action ran during these diagnostics.

The user later reported personally operating another owned Target (PID 34412) during its brief front/key transition. That transition cannot be attributed to launch alone. A direct regular Target retry (PID 36124) stayed background throughout a complete semantic set/read/capture round. These are separate processes and rounds.

The Human input failure has now been isolated to **fixture instrumentation**. A one-field, standard `NSWindow` App accepted real user typing; an empty `NSWindow` subclass accepted it; a subclass whose `sendEvent` only forwarded to `super` also recorded text changes. The variant that synchronously read an event number inside `sendEvent` failed to display input. A deferred variant crashed twice: both exact crash reports for PIDs 41235/41264 show `SIGABRT` at `NSEvent.eventNumber` from the fixture's event logger. Apple's [NSEvent contract](https://developer.apple.com/documentation/appkit/nsevent/eventnumber) restricts `eventNumber` to mouse/tracking events and raises an exception on an unsupported type. The original Focus fixture also incorrectly read `eventNumber` for keys in two logging paths. That bug was fixed by reading `keyCode` only for keys, `eventNumber` only for mouse events, and logging metadata after `super.sendEvent`.

The fixed one-field variant passed a **real user** round: the user saw typed text, the process did not crash, 12 key-down/up pairs for key code 18 appeared in `window_event`, and field-length changes occurred while it was front/key. A background direct-send key self-test on the corrected Focus Target likewise produced `keyCode=18`, a 0→1 field-length change and no crash without becoming frontmost. Input text was never logged. [The minimal build/reproduction steps](MANUAL_FOCUS_STEP.md) and [bounded evidence](evidence/checkpoint-5.json) retain exact binary, log and crash-report hashes. This repairs the **Human fixture validation**, not the DTW foreground click business effect.

One authorized live input-priority subtest then ran with the corrected Human window and a separate owned Target. While the user held a non-sensitive key, the Human log recorded 31 key-down and 31 text-change events during the coordinator interval, all while front/key; the Target recorded zero non-timer events and never became front/key. The foreground coordinator waited 3,022 ms, returned `user_active`, and logged `waiting → released` with **no `acquired`**. It did not call native input or move the pointer. The Target's exact-window grant was unresolved, so this passes **pre-borrow user-input deferral only**. It cannot pass physical foreground delivery, two-Agent contention, mouse preservation or post-borrow restoration.

A POC-only pre-borrow event-age gate waits for 600 ms without key, mouse-button, movement or scroll activity (up to three seconds). The above live round validates its refusal under sustained input, but it cannot eliminate a race after borrowing begins. There is no justified reproduction probability for the added `画`: the older fixture and user activity were confounded, and the repaired fixture has not yet accompanied a real DTW foreground borrow. Foreground business effect, cross-Session physical contention, mouse preservation and restoration under actual typing remain blocking failures.

## Model-facing output measurement

For a fixed cross-call JS state read, the MCP client received 19 UTF-8 text bytes, 56 structured JSON bytes and a 248-byte marshalled Go MCP result. For a fixed **real native observe**, default text was 120 bytes, structured content 242 bytes, and the complete MCP result 536 bytes; an explicit `result` query was 5,486 structured / 5,780 total bytes. The printed fact occurs in **both** default text and structured content. These are actual official-SDK client results and a bounded byte/duplication measurement. Full observation details and original receipts remain queryable by execution ID only while this POC server lives.

Now a **dedicated no-business Go SDK MCP** has supplied actual model-adapter evidence. Its sole `exec` returns fixed `probe=42; status=ok`; in dual mode it also returns structured `print/status/value`, in single mode no structured facts. Four identical-prompt `codex exec --json` runs called only this tool. The completed tool event showed both text and structured content to the adapter in dual mode; the model answered `status=ok, value=42` in every run. Whole-turn input tokens were dual **31,816 / 31,822** and single **31,810 / 39,382**; output tokens were **61 / 67** and **67 / 75**. Cache hits differed widely. [The bounded traces and hashes](evidence/model-token-probe.json) show that duplication is real, but the variation makes a savings percentage unjustified. This does not yet measure the production-shaped DTW result in a fixed installed agent/Skill context. Official OpenAI documentation describes `codex exec --json` event traces and `turn.completed` token usage in its [evaluation guide](https://developers.openai.com/blog/eval-skills).

A further [real POC model trace](evidence/real-poc-model-probe.json) used the built native Go POC binary with `DTW_POC_HELPER` empty. The model called its sole `exec` once with `print("probe=42")`. The adapter received text `probe=42\nexecution_id: model-probe-1` **and** structured `{"execution_id":"model-probe-1","print":["probe=42"],"state":"completed"}`; the model answered correctly. Whole-turn usage was 39,466 input / 98 output tokens, with 26,624 cached input tokens. This proves model integration of the new Go/QuickJS MCP chain without desktop effects; the POC Skill was not installed or automatically selected, and whole-turn numbers are not a result-size savings estimate.

Checkpoint 5 used an isolated scratch git repo with `.agents/skills/desktop-world-native-go-poc` pointing to the POC [Skill](SKILL.md). A real `codex exec` trace includes the model's command reading that exact `SKILL.md`, one call to the POC's sole MCP `exec`, the printed `skill-loaded`, and the four exact documented limits. Another scratch trace used two `exec` calls to preserve JS state across calls. This proves actual scratch Skill loading and use, without claiming product installation.

Two **full model-task attempts** with the native helper and exact owned window both stopped before a write. The first revealed an incorrect model comparison of a `name` fact to a string; the Skill was corrected to use `name.status`/`name.value`. The second used that shape but hit real desktop AX `dirty:true`, `truncated:true`, `ax_partial`, with no continuation; it queried the original result and stopped safely. A later grant-first, app-scoped programmatic read passed once but a new Session's grant subsequently returned `unresolved`, including three refreshes, so a third paid model retry would add no defensible full-task proof. The full model business task remains **unpassed**.

The **actual model adapter trace** exposes both default `content` and `structured_content` for these calls. In the Skill print-only call, their serialized sizes were 76 and 85 bytes, with the printed fact duplicated. In the first full-task `exec`, they were 515 and 617 bytes, again duplicating the printed fact. In the second task, the default `exec` was 227 and 350 bytes; the explicit original `result` kept the same 227-byte text and expanded structured content to 16,561 bytes. These are fixed observed adapter payloads, not an estimated token count. Trace hashes and whole-turn input/output counts are in [checkpoint-5 evidence](evidence/checkpoint-5.json); whole-turn token variation cannot be interpreted as a tool-result savings percentage. SDK client byte counts above remain separate evidence.
