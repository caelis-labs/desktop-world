## Current chain and directly tested results

- The current built arm64 Go POC binary SHA-256 is `b5a50d9706a62e39994bb8fa1284255a339700aa732667c154e5450e405750f0`. `otool -L` lists macOS frameworks/system libraries and no Node; an **actual built binary** under `PATH=/usr/bin:/bin` serves the official Go MCP SDK and lists exactly one tool, `exec`. Its `exec` operation runs a JS `await`/filter/print batch, then another call reads persistent `state`. The isolated matching [POC Skill](SKILL.md) names `exec` and `dtw`; agent installation/loading is still untested. The public schema exposes no transport choice.
- QuickJS now lives in a same-binary child process. The MCP parent retains the native helper and receipt ledger. A test-only blocked Go callback wedged the script child for five seconds; `status` and `cancel` remained live on the same connection, the child was killed after the cancellation watchdog, `result` reported `state_lost`, and a later `exec` refused to silently recreate state. Ordinary infinite loops before/after `await` interrupt cooperatively. `go test -race ./...` and `go vet ./...` pass in the nested POC module.
- An actual native `observe` traveled through Go MCP → child QuickJS Promise → parent → existing native helper. The default response retained `complete:false`, `truncated:true`, `more:true`; `result` retained the original native reply. A real owned AppKit semantic `set_value` and native read returned the exact Unicode value; a current-window `window_content` PNG was returned as MCP `ImageContent` only on `result(include_image:true)`.
- Three **real background AppKit semantic control** scenarios passed through the new chain: `set_checked`, `set_selected`, and `set_expanded` each ran true, repeated true, false, true. Each native action reported semantic channel, verified state, no foreground borrowing; the repeated true was `delivery:not_applicable`, with no extra App callback. The App independently logged exactly three transitions. Separate check and selection rounds also used semantic `invoke`; the App recorded `approved=order-42` and `ordered=Order A,Order B`. These are controlled App effects, beyond receipt-only evidence.
- Two independent MCP Sessions/native helper processes wrote the **same owned App** with nonoverlapping cross-process lock intervals (541/535 ms in the final reference-isolation round); both writes reached the App. On two **different owned Apps**, lock intervals overlapped (543/555 ms) and each App received its own write. Session B's attempt to use Session A's native Ref returned `permission_denied` and no foreign value reached either App. During another same-App contention, cancelling waiting Session B prevented its write while Session A completed one real write. These prove background parallelism, same-App serialization, Ref isolation and one-sided cancellation for the tested path. Physical foreground arbitration is still unproved.
- A real background semantic write reached an owned App once, then the waiting JS execution was cancelled before its deliberately delayed native reply. The parent retained the **original** native receipt, queried by the same execution ID; it reported `outcome:completed`, complete delivery, verified semantic step and `restoration:not_borrowed`. The App recorded the exact value once. [Original late receipt](evidence/late-native-original-receipt.json) identifies Run `run-05cca19f1d5fa9cb492f92b9`; the POC did not replay the action.
- A separate two-Session native grant round used only the owned background Target App. Session A wrote a controlled value, revoked its exact window grant through `dtw.revokeGrant`, then received `permission_denied` on its next write; App change count and native readback remained unchanged. Session B had its own active grant before A revoked and afterward wrote a second controlled value, independently verified by native readback and the App's second callback. The fixture never became frontmost, active, or key while launched with `open -g -n`. [Bounded evidence](evidence/grant-revoke-peer.json) records the raw owned-App log hash. Script authority can be reduced through `dtw`; it cannot self-grant.

## Foreground and user-input failure

The original FullFixture test (preceding checkpoint) had one submit callback with `POC-中文🙂画`, after a native read of `POC-中文🙂`; its cause remains unknown. The user was operating the desktop then, so misdirected real/IME input is plausible but unproven.

This checkpoint added an owned focus/input-logging App and saved [an original click receipt](evidence/focus-round-c-original-receipt.json). Across ten controlled clicks, the native receipt reported `outcome:completed`, `delivery:complete`, `channel:foreground_transaction`, `restoration:restored`; foreground occupation was 119–260 ms (median 128.5 ms). **Zero of ten** produced the target App's submit callback or local pointer event. During recorded borrowing the target PID briefly became frontmost/active while the App window's `isKeyWindow` stayed false. This is a failed business-effect gate; native `verification:not_requested` never meant the submit was verified.

The six-round attempted real-user-input comparison is **invalid** for mistargeting probability: target and Human fixture windows initially occupied the same coordinates, and the Human fixture logged zero keys. The user reported that the Human window could not be focused or clicked and that DTW moved the mouse. We stopped the foreground rounds and terminated both owned fixtures. The fixture now places the Human window separately, defaults it to foreground, primes its text field, and redacts text from both fixture logs. [The build script](build-focus-fixtures.sh) produces two distinct, locally signed macOS app bundles with separate bundle identifiers; compilation, plist and signature validation passed.

In a **Human-only follow-up without DTW**, the new bundle launched but was initially visible without being active or key. A separate `open -a` activation made it frontmost and key. The user could then click the window but twice could not enter text, including a double-click followed by one digit. The owned App log counted zero local mouse/key events and maximum field length 0 despite seven key-window transitions. The raw local log was not committed; [bounded metadata](evidence/human-focus-followup.json) was. This confirms the input lane is still unusable; it does not explain whether the OS, fixture event handling, or user interaction surface dropped events. The source now instruments `NSWindow.sendEvent` and retries activation after the run loop starts, but that **new build is not live accepted**. The Human app was terminated after the attempt.

A POC-only pre-borrow event-age gate now waits for 600 ms without key, mouse-button, movement or scroll activity (up to three seconds); it has **not** been live accepted and cannot eliminate a user input race after borrowing begins. There is no justified reproduction probability for the added `画`; no further foreground success claim follows from these samples. Foreground contention, user-input precedence, mouse preservation and restoration under actual typing remain blocking failures.

For a fixed **real native observe**, default text was 120 bytes, structured content 242 bytes, and the complete MCP result 536 bytes; an explicit `result` query was 5,486 structured / 5,780 total bytes. The printed fact occurs in **both** default text and structured content. These are actual official-SDK client results and a bounded byte/duplication measurement. No model-token accounting, installed adapter forwarding trace, or token-savings percentage has been verified.
