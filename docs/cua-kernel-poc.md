# DTW thin CUA kernel POC

For the final package, corrected fresh-Agent acceptance, and remaining release limits, read [the convergence report](cua-thin-final-poc.md). This file records the initial goal and technical selection.

## Goal and selection

Useful desktop task completion takes priority over compatibility with today's DTW implementation. Preserve the product shape: App → Window → Element discovery, one `exec` MCP tool, scripts and session state, compact results with exact result lookup, background input when CUA can deliver it and controlled foreground input otherwise, no Node requirement, isolated Agent sessions, and a small installable plugin. The public script API is CUA's `cua` API for this POC; no `dtw.app` compatibility promise.

Pin upstream CUA Driver source at `ac967b9006aafa10870aadb5a645b038cba9721a` (MIT). The prototype links `cua-driver-sdk` as an `rlib`, calls a trusted immutable Session, and delegates JavaScript to CUA `run_script`. It does not port native AX/capture/input, expose the 59 upstream MCP tools, embed a second JavaScript engine, or use a Node runtime. A single private `cua-driver` worker is spawned directly by the SDK with inherited pipes, no reusable socket and no CuaDriver App. CUA owns native execution, native references, authorization and input routing. The adapter owns MCP framing, compact output/result retention and the optional JSON `state` handoff between script calls. The public `session` is an adapter label mapped to a CUA trusted Session: it partitions JSON state and receipts, while native element tokens and the desktop remain shared in one worker. Separate Agent hosts normally start separate MCP processes and workers; no strict desktop isolation is promised.

The private worker is selected over same-process `CuaDriver::create`: CUA explicitly returns `facility_unavailable` for the macOS cursor overlay in an arbitrary direct runtime. The worker is the upstream-supported overlay path. Its current SDK request path serializes worker calls behind one mutex. A cancellation request can be recorded immediately by the adapter, but this does **not** prove prompt interruption of a running worker action. The POC must report `cancel_requested` until CUA returns a terminal receipt; if prompt cancellation is a product gate, CUA needs a worker cancel channel or an SDK extension. Killing the shared worker would lose both Sessions and could leave action outcome unknown.

The adapter has no authority to grant macOS Accessibility or Screen Recording. In Bot integration Bot must directly spawn and own its private child, and the actual responsible Bot process must receive its own OS grants. In standalone Agent use the actual Agent host's responsibility chain and grants govern access. Direct `posix_spawn`/`Command` is required; launching a standalone CUA app through LaunchServices is outside this topology. TCC inheritance and overlays must be confirmed on a real signed host before migration.

## POC gates

Evidence labels: **source** means inspected behavior, **fixture** means automated isolated test, **live** means real app effect read back independently, **Agent** means a fresh Agent used this plugin and completed the task. No lower label implies a higher one.

| Gate | Required observation |
| --- | --- |
| Build/distribution | One `dtw` binary plus private `cua-driver`, one MCP `exec`, short Skill, MIT notice; starts with Node absent and without CuaDriver App. |
| Discovery | Real app/window/element discovery, exact window identity and screenshot; stale element rejected and fresh observation recovers. |
| Input | Semantic click/type, keys, menus, drag, background route and controlled foreground fallback have independent effect readback. No action on WeChat or private content. |
| Cursor | Visible virtual cursor succeeds via private worker, or exact `facility_unavailable`/permission blocker is reported. |
| Sessions | Two labels maintain independent adapter JSON state and receipts. Native snapshots/tokens can affect one another in a shared worker, as can Agents on the same desktop; refresh state before acting. A cancel request retains original execution id and terminal outcome; unknown is never replayed. |
| Output | Large AX tree and screenshot are bounded in model text, with explicit truncation and retrievable full result; key error code/message never removed. |
| Permissions/lifecycle | Refusal has no desktop action, host attribution is measured, process exit reaps its private worker, and no second App is needed. |
| Original failed demos | Fresh Agent session with only this thin plugin attempts isolated Chrome `READY-20261011` → `CLICKED-20261011`, Obsidian discovery/screenshot/Cmd+P without notes, and temporary WPS DOCX marker/save/textutil readback. These were planned but not performed in the earlier CUA evaluation because TCC was pending. |
| Platforms | macOS real app acceptance is required for this POC. Windows cross-build is only build evidence; no Windows GUI pass without a real Windows machine. |

## Upstream unified entry versus this adapter

At the pinned CUA SHA, `run_script` is already the script engine and the correct App → Window → Element abstraction. It directly supports `getApp` (unpinned bindings follow the app's front window), `getState` with query/diff/screenshot options, `query`, `waitFor`, `verify`, semantic and pixel actions, `zoom`, and window or desktop-targeted `hotkey` through its allowlisted `cua.call`. It is not necessary to port these atomics or implement another interpreter. The full native inventory additionally includes `run_steps`, `invoke_menu`, `get_desktop_state`, typed browser/CDP tools, permissions, cursor, recording, and configuration. These are **not all script-callable**: `run_script` expressly excludes `run_steps`, native menus, full-desktop capture, browser-specific tools and another `run_script`.

Directly exposing upstream `run_script` is feasible if the host can accept upstream MCP's broader advertised tool table, short-lived JS state, and upstream result shape. It is simpler and preserves CUA's own permission path. At this SHA, an upstream policy can narrow advertised tools, but allowing only `run_script` also denies the nested native action/read tools that its scripts invoke. A single visible MCP tool with a working script allowlist therefore still needs a small MCP facade or a targeted upstream tool-visibility feature. The POC facade also adds persistent JSON `state`, original execution receipts with status/result/cancel, bounded default output, full structured/text paging, on-demand images, and host-owned private worker packaging. Those are product affordances, not new native execution. Their cost is adapter code, extra Session bookkeeping, serialized worker calls, delayed cancellation and a possible mismatch between the public Session label and native shared screen/reference state. None fixes OS authorization or makes concurrent Agents' focus independent.

The new narrow `exec` operations `menu` and `desktop` pass straight through to upstream `invoke_menu` and `get_desktop_state`, preserving native validation, authorization and results; no generic 59-tool router is exposed. `run_steps` is deliberately not surfaced because its built-in stale-token re-find may retry a step, conflicting with this POC's expired-reference/no-replay gate. Typed browser tools are documented as an alternative for page-aware, explicitly authorized browser work, not embedded into the native screenshot path or silently attached to a personal profile. For large pages, the default one-tool path can take a screenshot with `include_accessibility_tree:false`, return only metadata, view the retained image on demand, and act on exact window-local pixels with a `capture_id`; AX queries remain available for text and verification.

Source pin and development location are temporary POC inputs. Proposed eventual artifact is `bin/dtw`, `libexec/cua-driver`, `skills/desktop-world/{SKILL.md,api.d.ts,RECIPES.md}`, `mcp.json`, `plugin.json`, MIT/MPL licenses and `THIRD_PARTY_NOTICES.md`. Rebuild/sign nested worker under host packaging. Product migration, push, PR and release are out of scope.
