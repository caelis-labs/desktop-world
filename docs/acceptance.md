```sh
python3 tests/acceptance/native_ops_probe.py /path/to/package/bin/dtw
```

Real GUI harnesses in `tests/acceptance/` launch temporary Chrome, Obsidian, or WPS instances and may take foreground focus. They are manual, not CI tests. ## Upstream release compatibility probe on 2026-10-11

The newest published CUA Driver release checked here was `cua-driver-rs-v0.34.1` at source commit `0c69d9a2c8abbb5051a2df4a23f0fa166d5385dc`. Its official macOS universal binary archive was downloaded into `/private/tmp/dtw-cua-release-0341-probe-20261011`, and its SHA-256 `52de49b5046df19245ad02ff9aa89ce9caf69e84988e1d0fac677611dd83e48c` matched the release's `SHA256SUMS`. The binary returned `cua-driver 0.34.1` for `--version`. That bare binary archive's embedded arm64 signature did not pass `codesign --verify` on this Mac; this observation is specific to the bare universal-binary asset and does not assess the full app archive.

For an isolated compatibility check, a copy of that worker was ad hoc signed in the temporary directory and paired with the v5 DTW adapter. The desktop-independent `mcp_smoke.py` failed on its first script with `Unknown tool: run_script`. Inspection of the exact v0.34.1 tag source also found no `run_script` tool, whereas the POC's pinned `ac967b9` source implements it. This is a release-feature mismatch, not a failed desktop permission or fixture. The release SDK was not separately built because its worker lacks the sole script primitive required by this DTW interface. Keep the adapter and worker on the tested source pin until an upstream release with `run_script` is available and passes the same contract and live tasks.
